# Images are uploaded to a feed, served under the read id, and stored as sent

## Context and Problem Statement

Notes are markdown files and the web UI renders markdown, but there was nowhere to put a picture a note could show, and a feed had no picture of its own. Issue #12 asks for it in one line: "Add images: title images for feed; images in the markdown". The decisions below were made on the owner's behalf while working on it, so each is stated with its reason, to be reviewed and overruled where the owner disagrees. Where do images live, who may add them, who may see them, what is checked on the way in and out, and what does notefeed do to them? (Issue #12, building on ADR 0001, ADR 0005, ADR 0008, ADR 0009 and ADR 0010.)

## Decision Drivers

* Notes stay plain markdown files that can be read, grepped and kept in git (ADR 0001).
* An image must show wherever its note shows: the feed page, the read-only view and RSS readers, which have no password to send.
* The feed's name is the write key on an open feed and must not leak through a public URL (ADR 0001, ADR 0004).
* The same checks and the same write path for the web UI, scripts and the client packages (ADR 0005, ADR 0008).
* An uploaded file is served from the app's own origin, so a file that is really something else must not be able to run there.
* No database and no new dependency, in particular no native image library (ADR 0001).
* Safe by default on a public open instance, but with no features that need a second delete path yet.

## Considered Options

How a note holds an image:

* **Upload, then reference:** an image is uploaded to the feed and gets a URL; the note uses it as ordinary `![alt](url)` markdown.
* **Embed:** the image's bytes go into the note as a `data:` URI.
* **Attachments tied to a note:** the image is stored with one note and removed with it.

Where an image is served, and who can fetch it:

* **Under the feed's read id,** `/r/<read id>/images/<file>`, with no password.
* **Under the feed's name,** like the feed page, with the same password checks.
* **A separate signed URL** per image.

What is checked and what is served:

* **The file's first bytes** decide the format; the response headers stop a browser from treating it as anything else.
* **The `Content-Type` the sender claims** decides the format.
* **SVG as well,** after sanitising it.

What is done to a stored image:

* **Nothing:** the bytes are stored as sent, under a name made from their hash.
* **Processing:** resize, re-encode and strip metadata.

## Decision Outcome

Chosen options: upload then reference, served under the read id without a password, format decided by the bytes with defensive response headers, no SVG, content-addressed names and no processing, because together they add images with the smallest new surface: no second kind of note, no new credential, no new storage format and no dependency.

* **Upload, then reference (a).** `POST /api/v1/feeds/{feed}/images` stores the bytes and answers `201` with `file` (the stored name), `url` (absolute) and `markdown` (`![](url)`). The note then contains that markdown like any other text. Markdown already renders an image for any URL, so reading, editing, searching, git and RSS keep working without a change, and an image can be used in more than one note. Embedding as a `data:` URI would make every note as large as its pictures, put megabytes of base64 into the markdown file and the RSS description, hit the 100 KB note limit with one small photo, and make a note unreadable in a text editor. An attachment tied to one note would need a second kind of thing to create, move and delete together with its note, an upload before the note exists (a new note has no id yet), and would break as soon as an image is used in two notes. The cost of upload-then-reference is that nothing ties an image to a note, which is the first consequence below.
* **Who may upload (b).** Whoever may post to the feed, with the same checks in the same order: the instance password, then the feed's password (ADR 0008), then the per-client rate limit, and then the body is read. Uploads count toward the same `NOTEFEED_RATE_LIMIT` as posts. This is the access ADR 0009 and ADR 0010 chose for editing and deleting, for the same reason: there are no accounts.
* **Uploads only to an existing feed (c).** A feed is created by its first note and can only get a password then (ADR 0008). An upload to a feed that does not exist answers `404` and creates nothing, not even a directory, so an upload cannot create a feed that then has no password. The web UI therefore shows no **Add image** button on a feed that has no note yet. An upload to a feed that has no read link (ADR 0010) is `404` too, because its image would have no URL. An upload racing with the deletion of the feed is also `404`, and does not bring the folder back; the read id is checked again after the body is read, so an upload that stalled while the feed was deleted and created again (the way to add a password) is refused as well. A feed that had notes and lost them all still exists, still has its read id and still accepts uploads, and the answer carries a URL: whoever may upload may post a note, and the answer to that post carries the same read link, so nothing is disclosed that posting does not.
* **Served under the read id, with no password (d).** An image is fetched from `/r/<read id>/images/<file>`. A note's images have to show on the feed page, in the read-only view and in feed readers, and the last two have no password to send; the read link is already the thing that makes a feed readable without one. So an image is exactly as public as the read link: it needs no password, even on a locked instance or a protected feed, and anyone who has an image's URL can fetch it. Under the feed's name it would need the instance and feed passwords, so images would be broken in the read-only view and in every RSS reader, and the name, which is the write key on an open feed, would be written into every note that shows an image and into the RSS feed. A separate signed URL per image would need a secret and an expiry or a stored token, would make a note's markdown change when a URL expires, and would still have to be fetchable by a reader without a password, so it protects nothing the read id does not. The feed's name never appears in an image URL. An unknown read id, a malformed file name or a missing file answers `404`, so the URL does not say which of them it was. This route is not under `/api/v1`: it answers bytes, like the RSS route.
* **The format is decided by the bytes (e).** PNG, JPEG, GIF and WebP are recognised by their first bytes (the PNG signature, `FF D8 FF`, `GIF87a` or `GIF89a`, `RIFF....WEBP`). The `Content-Type` of the request is not used: it is sent by the client and can say anything, and a file that says `image/png` but is HTML is refused with `415`, while a PNG sent as `text/plain` or `application/octet-stream` is accepted. Because the stored name has the extension of the detected format, the type a browser is told is the extension's, never the sender's. Only the header is checked, so a file can be a valid image header followed by something else (a polyglot, such as a PNG header followed by HTML). The files are served from the app's own origin, so that is the real risk, and the defence is in the response, not in more checking: every image is sent with `X-Content-Type-Options: nosniff` (the browser may not guess a different type), `Content-Type` from the extension, and `Content-Security-Policy: default-src 'none'; sandbox` (if the file is opened as a page it runs in a sandbox with no scripts, no forms and no access to the app's cookies or storage). Doing more validation, such as decoding the file, would need an image library and would still not remove the need for these headers.
* **No SVG (f).** SVG is an XML document that can contain script and links, and is the one image format a browser executes. The headers above would contain it, but a format that can only be made safe by those headers is not worth having for a first version, and nobody asked for it. SVG is not accepted, and a file that is not one of the four formats is `415`.
* **Content-addressed names (g).** An image is stored as `DATA_DIR/<feed>/.images/<first 32 hex characters of its SHA-256>.<ext>`. Uploading the same bytes twice gives the same URL and one file, which dedupes repeated uploads (for example the same screenshot pasted again). A URL's content can never change, so the response says `Cache-Control: public, max-age=31536000, immutable` and browsers and proxies keep it for a year. A name made from the content cannot be guessed by counting: a sequence number would let anyone who has one image URL walk to the next. Such a name is also not a path a request can choose: a file name is checked against `^[0-9a-f]{32}\.(png|jpg|gif|webp)$` before any path is built, so `..`, dot files such as `.password`, upper case and other extensions never reach the disk. It is 128 bits of the hash, which is enough to avoid accidental collisions. The write uses a temporary file and an exclusive link, like notes, so a concurrent upload of the same image is harmless and an existing image is never overwritten.
* **No processing (h).** Images are stored byte for byte: no resizing, no re-encoding, no thumbnails and no metadata stripping. Doing any of that needs a native image library, which would make the Docker image and the build platform-dependent, and would add an attack surface that parses untrusted files in the server's process. The cost is stated plainly: EXIF data in a photo, including the GPS position where it was taken, the camera and the time, stays in the stored file and in what readers download, and the file is public to anyone with the read link. The documentation says so where images are explained (posting, web UI, operations, and the client READMEs); the operations page names a tool (`exiftool`) to remove it before uploading.
* **Limits (i).** `NOTEFEED_MAX_IMAGE_BYTES` is the size of one image, 5242880 (5 MiB) by default; over it the upload answers `413` and nothing is written, and a body without a `Content-Length` stops being read at the limit. The value is clamped to 10 MiB (10485760) whatever is configured: the request passes through Next's proxy, which buffers a body only up to 10 MiB and passes on the rest cut off, so a larger limit would store truncated images. A body that ends before the `Content-Length` it declared is refused (`413`) for the same reason, and nothing is stored. `NOTEFEED_MAX_IMAGES_PER_FEED` is the number of images in a feed, and defaults to `0`, no limit: when it is reached, a new image answers `507` (`image_limit`), but uploading one the feed already has does not. It is off by default because there is no way yet to delete one image (below), so a limit a user hits could only be cleared by deleting the feed or removing files by hand. An operator of a public open instance can set it, together with the existing caps. The check is not locked, so several uploads at the same moment can overshoot it by a few, as the other caps can. Uploads count against the per-client rate limit as posts, so a script cannot fill the disk faster than it could post.
* **No list or delete yet (j).** There is no endpoint to list or delete images, in the API, the web UI or the clients. Images are removed when the feed is deleted (ADR 0010). Deleting a note does not delete its images: another note may use the same one, and finding out would mean parsing every note's markdown. This is the second consequence below. A management endpoint can be added when someone needs it, and the cap can then be turned on by default.
* **The title image is a feed setting (k).** The settings from ADR 0010 get an `image` field, which names one of the feed's own uploaded images by its file name. In `PUT /api/v1/feeds/{feed}`, leaving `image` out keeps it, an empty string removes it, and any other value must be an image this feed has, or the answer is `400`: a name is never turned into a path unless it passes the same check as above, so a setting cannot point at another feed's image or at a file that is not an image. `GET` of the feed and of the read feed answer `image_url` (absolute, or `null`). The title image shows in the page header and the read-only view, and is the RSS channel's `<image>`. A locked feed's page shows only the unlock form, as with the title. The title image is public like the title and the description. A title image whose file has been removed by hand (the way an operator removes an image) counts as none: the page, the API and the RSS feed show no image, and saving the title or the description, which leaves `image` out, still works. Only an `image` that is given is checked.
* **Web UI.** The compose box and the note editor share one component with an **Add image** button, paste and drag-and-drop. It uploads through the same API and inserts `![](url)` at the cursor; refusals show next to the box. This needs JavaScript: without it the text box still works, and an image can be used by its URL. Rendered images load lazily and are never wider than the column. The feed settings get a **Title image** control with **Choose image** and **Remove image**.
* **Clients.** Both packages get an upload method (`uploadImage`, `upload_image`) that sends the bytes as `application/octet-stream`, because the server ignores the claimed type, and `updateFeed` / `update_feed` can set or clear `image`. Both CLIs get `notefeed image <PATH>`, which prints the markdown to put in a note.
* **No MCP tool (l).** An image is binary, and a tool call carries text; encoding it as base64 in a tool argument is what an assistant is worst at, and the result would be a very large message. An assistant can still use an image that someone uploaded by writing its URL into a note. A tool can be added when there is a good way to hand over a file.
* **Documented in the OpenAPI description.** The upload is the operation `uploadImage` and the generated clients are regenerated from it, so the spec stays the source of the clients (ADR 0006).

Out of scope: SVG, video, thumbnails, galleries, resizing, removing metadata, proxying images from other sites, and listing or deleting single images.

### Consequences

* Good, because notes remain plain markdown and every existing feature (editing, RSS, git, search) works on notes with images unchanged.
* Good, because an image shows everywhere its note shows, with no password and without exposing the feed's name.
* Good, because a file that only pretends to be an image cannot run as a page from the app's origin: it is served as the type of its detected extension, with `nosniff` and a sandbox policy.
* Good, because repeated uploads cost no space and an image URL can be cached for good.
* Good, because there is no new dependency and no change to how existing feeds are stored.
* Bad, because images are as public as the read link. Anyone who has the read link, or an image's URL, can fetch the image, and anyone who has the read link can hot-link an image from another site, using this instance's bandwidth. Nothing private should be uploaded.
* Bad, because EXIF data, including GPS position, stays in the stored file and is public to those who can fetch it. notefeed does not remove it.
* Bad, because orphaned images accumulate: deleting a note, or replacing a title image, leaves the file, and it stays until the feed is deleted or the file is removed by hand (see Operations). With no per-feed cap by default, an open instance's feed can take disk space until the operator sets `NOTEFEED_MAX_IMAGES_PER_FEED` or deletes the feed.
* Bad, because the `url` in a note is absolute and built from `PUBLIC_URL` (or the request) when the image is uploaded. If the instance's public address changes, every image in an existing note points at the old address and breaks until the notes are edited.
* Bad, because deleting a feed removes its images, and a copy of a read link or image URL that someone kept stops working: the image answers `404` for good, since a re-created feed has a new read id (ADR 0010). This is intended.
* Bad, because backups must now include the `.images` folder in each feed folder. A tool that skips hidden folders loses the images, and the notes then show broken images.
* Bad, because the per-feed cap is checked, not locked, so concurrent uploads can overshoot it by a few.
* Bad, because a polyglot file is still stored and served. It cannot run from the app's origin because of the response headers, but a browser that does not honour `nosniff` or `sandbox` would be exposed; the defence depends on those headers staying on every image response.

### Confirmation

Vitest covers each format's real header and the refusals: SVG, HTML, an empty body and a PNG header with a wrong `Content-Type`; that the name is 32 hex characters of the SHA-256 plus the extension; storing the same bytes twice (one name, one file); an unsupported type writing nothing; the per-feed cap, refusing a new image and not a repeat; that a feed that does not exist is not created; and that a name with `..`, a dot file, upper case or another extension never reads a planted file, in serving and in the settings. The HTTP tests cover the upload (`201` with `file`, an absolute `url` under the read id and `markdown`; `404` for a missing feed with no directory made; an over-limit body as `413` with nothing written, including a chunked body that stops being read at the limit; `507` `image_limit`; `401` for a protected feed or a locked instance; the rate limit; a feed deleted before the write), serving (the bytes with the four headers, also for a protected feed without a password; a PNG-headed HTML payload served as `image/png`; a wrong read id, a bad name or a missing file as `404`; the feed's name not serving it; a deleted feed's images gone), and the `image` setting (round trip through the API, the read API, `GET` of the feed and the RSS channel `<image>`; omitted keeps it, empty clears it; another feed's image is refused). Both client packages have tests for the upload method (raw bytes as `application/octet-stream`, per-call feed and feed password, the error classes for `415`, `413`, `507` and `404`), for setting and clearing `image` in `updateFeed` / `update_feed`, and for `notefeed image` (the printed markdown, the bytes sent, exit codes). The Playwright spec `e2e/images.spec.ts` covers the web UI: no **Add image** button on a feed without a note, an image added in the compose box showing on the feed page and in the read-only view, the same control in the note editor, a title image shown in the header and the read-only view and removed again, and a file that is not an image refused. Paste and drag-and-drop in the browser have no test of their own, and nothing tests the behaviour of a real browser with a polyglot file: that rests on the headers, which the HTTP tests check.
